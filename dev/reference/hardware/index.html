    Chips¶

    9 chips. Figures are nominal and per GPU. Most come from vendor datasheets; the others come from published simulator descriptors, vendor APIs or public measurements, and each file's notes say which. See Sources. What a chip achieves in practice is a coefficient in blis-registry.

    Rack-scale chips¶

    On these chips an NVLink domain spans a rack of several nodes, so a third tier sits between the node and the inter-node fabric. Traffic that leaves the rack uses the fabric the scenario names.

    gb300 4 72 900 900

    Each file records the source of its figures, and any conversion applied to them, in its _comment keys. They are reproduced here as written, including where a figure is not a datasheet figure.

    _comment Alias for A100-SXM — defaults.yaml uses A100-80 for all A100 model entries (BC-14).

    _comment_interconnect IntraNodeBwGBps is the on-package NVLink 3 link as a per-GPU NOMINAL unidirectional bandwidth in GB/s (alias of A100-SXM; same interconnect). vendor_spec (bidirectional / 2), NOT measured effective throughput; any measured correction is a per-cluster blis-registry number. The inter-node fabric figure and the intra:inter ratio it feeds (#1530) live with the reusable Network fabric class (networks/roce-200g.yaml), paired with this chip per deployment (a cluster/pool concept, #1662).

    _comment_sm SMCount is the count of enabled Streaming Multiprocessors on the GA100 die as shipped in this part, from the NVIDIA datasheet (https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/a100/pdf/nvidia-a100-datasheet-us-nvidia-1758950-r4-web.pdf). A100 enables 108 of the GA100 die's 128 SMs. The cost model uses SMCount for two things: the per-SM share of peak FLOPs, and the 12-SM derate a Triton-path KV fetch withholds while it overlaps a forward pass (cost model §8.3), which is 9.09% at 132 SMs and 11.11% at 108.

    b200: provenance notes

    _comment B200 SXM. Peak FLOPs, HBM capacity and HBM bandwidth are the figures NVIDIA ships in AISimulate's own system descriptor (systems/b200_sxm.yaml), which is the same source the h200 and gb200 entries cite: dense BF16 2250 TFLOPS, dense FP8 4500 TFLOPS, dense FP4 9000 TFLOPS, 7.7 TB/s HBM3e. FP4 has native Tensor-Core support on this part, where on Hopper it is a bandwidth saving only. CAVEAT (memory unit): the descriptor states mem_capacity as 193273528320 bytes, which is exactly 180 GiB, so this entry records the GiB reading the source itself uses rather than converting.

    _comment_interconnect IntraNodeBwGBps is the NVLink 5 per-GPU unidirectional figure, 900 GB/s (1800 GB/s bidirectional per GPU / 2). A node's GPU count is a property of the deployment rather than of this part, so it comes from the scenario's cluster block; the common chassis is the 8-GPU HGX B200 baseboard. Unlike GB200 this part carries no rack tier: its NVLink domain is the baseboard, so crossing a node boundary is a bandwidth change and the fabric governs (networks/roce-200g.yaml at 50 GB/s per GPU is the descriptor's reference, CX7 400GbE RoCEv2). No GPUsPerRack or IntraRackBwGBps is stated here because there is no rack-wide NVLink domain to describe.

    _comment_sm SMCount is the count of ENABLED Streaming Multiprocessors on the two GB100 dies this part carries. 148, from NVIDIA's own Hot Chips 2024 Blackwell disclosure: each die physically contains 80 SMs and enables 74, giving 148 across the GPU (https://chipsandcheese.com/p/nvidias-b200-keeping-the-cuda-juggernaut, reporting that presentation's specifications table). NOT a datasheet figure the way the Hopper and Ada entries' counts are: NVIDIA's B200 datasheet publishes no SM count, and the AISimulate descriptor this entry cites for FLOPs and HBM (systems/b200_sxm.yaml) states none either, so this is the most authoritative public source rather than a vendor spec sheet. The cost model uses SMCount for two things: the per-SM share of peak FLOPs, and the 12-SM derate a Triton-path KV fetch withholds while it overlaps a forward pass (cost model §8.3), which is 8.11% at 148 SMs.

    b300: provenance notes

    _comment B300 SXM (Blackwell Ultra). Peak FLOPs, HBM capacity and HBM bandwidth are the figures NVIDIA ships in AISimulate's own system descriptor (systems/b300_sxm.yaml): dense BF16 2250 TFLOPS, dense FP8 4500 TFLOPS, dense FP4 14000 TFLOPS, 7.75 TB/s HBM3e, and a capacity the descriptor records as what nvidia-smi reports rather than as a datasheet figure. Two things distinguish this part from B200 and both are recorded because a cost model reads them: dense FP4 is 14000 TFLOPS against B200's 9000, a 1.56x step with no change to the BF16 or FP8 rates; and the descriptor's int8_tc_flops is 153.5 TFLOPS, three orders of magnitude below its FP8 figure. That INT8 value is transcribed by the source from a sparse TOPS number and is not consistent with the rest of the row, so this entry omits an INT8 field rather than carry a figure its own source contradicts.

    _comment_interconnect IntraNodeBwGBps is the NVLink 5 per-GPU unidirectional figure, 900 GB/s (1.8 TB/s bidirectional / 2), the same as B200. The inter-node fabric differs: the descriptor states 100 GB/s per GPU for a 1:1 CX8 XDR 800 Gb/s configuration, double B200's CX7, so a cross-node collective on this part pays half the penalty. That fabric figure lives with the reusable fabric class rather than here; no catalog fabric matches 100 GB/s per GPU yet, so a B300 multi-node scenario has no fabric to name. Single-node B300 scenarios are unaffected. Like B200 and unlike GB200 there is no rack-wide NVLink domain, so no rack tier is stated.

    _comment_sm SMCount is the count of ENABLED Streaming Multiprocessors, recorded as 148 for consistency with B200. CAVEAT (provenance is weaker here than on any other chip in this directory, and this figure is the one to challenge first if a B300 prediction is off): NVIDIA's Blackwell Ultra architecture blog states 160 SMs across the two dies in the full GPU implementation, and footnotes that available SM count and HBM capacity varies by SKU (https://developer.nvidia.com/blog/inside-nvidia-blackwell-ultra-the-chip-powering-the-ai-factory-era). It publishes no enabled count for the SXM SKU this entry describes, the AISimulate descriptor cited above for FLOPs and HBM (systems/b300_sxm.yaml) states none, and no NVIDIA datasheet gives one. So 148 is carried over from B200 by die-sharing INFERENCE, not cited: the true value lies between 148 and 160, and if it is 160 this entry understates the per-SM FLOPs share by 8%. Recorded rather than omitted because the cost model needs a number and B200's is the better-attested of the two candidates; it will be corrected when NVIDIA publishes a per-SKU count. The cost model uses SMCount for two things: the per-SM share of peak FLOPs, and the 12-SM derate a Triton-path KV fetch withholds while it overlaps a forward pass (cost model §8.3), which is 8.11% at 148 SMs.

    gb200-nvl72: provenance notes

    _comment GB200 in the NVL72 rack configuration. Peak FLOPs, HBM capacity and HBM bandwidth are the InferenceX /api/v1/views/gpu-specs figures for gb200 — the same source as every other chip here (calibration companion §5.2): dense BF16 2500 TFLOPS, dense FP8 5000 TFLOPS, dense FP4 10000 TFLOPS, 186 GB HBM3e at 8 TB/s. Two structural differences from Hopper carry over regardless of the numbers: FP4 has native Tensor-Core support here where on Hopper fp4Tflops is null, confirming FP4 is a bandwidth saving only on that part; and the CPU link is NVLink-C2C rather than PCIe, which changes the offload arithmetic. CAVEAT (memory unit): 186 GB is read here as decimal GB (173.2 GiB), where the H200 entry reads NVIDIA's advertised '141GB' as GiB. The two entries therefore apply different readings of the same kind of figure, because each follows its own source's units; the readings differ by 7.4% and the choice is not free of consequence for capacity planning.

    _comment_interconnect This part is the reason the topology needs three tiers rather than two. IntraNodeBwGBps is the NVLink 5 per-GPU published figure, 900 GB/s. A node here is one Grace-Blackwell tray — two Grace CPUs with two GPUs each — so GPUsPerNode is 4, not 8. IntraRackBwGBps is ALSO 900: the NVLink 5 switch fabric spans all 72 GPUs in the rack at full per-GPU bandwidth, so crossing a tray boundary inside the rack is not a bandwidth change at all. Only the rack boundary is, and it is an 18x step down to InfiniBand (networks/ib-400g.yaml, 50 GB/s nominal). A model keyed on tp > GPUsPerNode alone would wrongly derate this part: the condition is the link, not the chassis count. That 18x step at the rack boundary is what makes EP up to 72 viable within one rack, since at EP=72 no expert traffic leaves it. AISimulate's gb200 descriptor states the same three tiers, and adds inter_rack_latency: 5 µs — a rack-boundary latency figure the catalog has no field for, so it lives in blis-registry with the other floors.

    _comment_sm SMCount is the count of ENABLED Streaming Multiprocessors per GPU, 148: GB200 carries the same two GB100 dies as B200 at the same 74-of-80 enabled count, from NVIDIA's Hot Chips 2024 Blackwell disclosure (https://chipsandcheese.com/p/nvidias-b200-keeping-the-cuda-juggernaut, reporting that presentation's specifications table). This is a PER-GPU figure, not a per-rack one — the 72 GPUs of the NVL72 domain give the rack 10,656 SMs, but the cost model reads this field per device. NOT a datasheet figure the way the Hopper and Ada entries' counts are: the InferenceX /api/v1/views/gpu-specs record cited above supplies this part's FLOPs and HBM but carries no SM count, and no NVIDIA datasheet publishes one, so this is the most authoritative public source rather than a vendor spec sheet. The cost model uses SMCount for two things: the per-SM share of peak FLOPs, and the 12-SM derate a Triton-path KV fetch withholds while it overlaps a forward pass (cost model §8.3), which is 8.11% at 148 SMs.

    gb300: provenance notes

    _comment GB300 (Grace-Blackwell Ultra) in its rack-scale configuration. Peak FLOPs, HBM capacity and HBM bandwidth are the figures NVIDIA ships in AISimulate's own system descriptor (systems/gb300.yaml, citing https://resources.nvidia.com/en-us-blackwell-architecture/blackwell-ultra-datasheet): dense BF16 2500 TFLOPS, dense FP8 5000 TFLOPS, dense FP4 15000 TFLOPS, 8 TB/s HBM3e. This is the same source and the same reading b200, b300 and gb200-nvl72 already cite. Two things place this part between B300 and GB200: it carries the Blackwell Ultra die (dense FP4 15000 TFLOPS, a 1.5x step over GB200's 10000 and above even B300's 14000) at the higher 2500 TFLOPS BF16 rate of the Grace-Blackwell bin rather than B300 SXM's 2250, while keeping GB200's rack-scale NVLink domain. Like b300, the descriptor's int8_tc_flops is 165 TFLOPS — ~30x below its FP8 figure, a value the source transcribes from a sparse TOPS number and that is not consistent with the rest of the row; this entry omits an INT8 field rather than carry a figure its own source contradicts (the catalog has no INT8 field in any case). CAVEAT (memory unit): the descriptor records mem_capacity as 298013687808 bytes, labelled '284208MiB reported by nvidia-smi'. That byte count is exactly 284208 MiB, i.e. 277.5 GiB, so this entry records the GiB reading of the source's own figure rather than converting it to decimal GB — the same choice b200 and b300 make, and the opposite of gb200-nvl72, which reads its source's advertised decimal GB.

    _comment_interconnect Like gb200-nvl72 and unlike B200/B300, this part needs three topology tiers rather than two, and for the same reason. IntraNodeBwGBps is the NVLink 5 per-GPU unidirectional figure, 900 GB/s. A node here is one Grace-Blackwell tray — two Grace CPUs with two GPUs each — so GPUsPerNode is 4, not 8. IntraRackBwGBps is ALSO 900: the descriptor's inter_node_bw (NVLink via NVSwitch within the rack) equals its intra_node_bw, so the NVSwitch fabric spans all 72 GPUs in the rack at full per-GPU bandwidth and crossing a tray boundary inside the rack is not a bandwidth change at all. Only the rack boundary is, and it is a step down to InfiniBand: the descriptor's inter_rack_bw is 100 GB/s per GPU (CX8 XDR 800 Gb/s), double the gb200-nvl72 rack-boundary reference. That inter-rack fabric is a property of the cluster, not the die, so it lives with the reusable fabric classes rather than here; no catalog fabric matches 100 GB/s per GPU yet, so a GB300 inter-rack scenario has no fabric to name (the same gap B300 notes for its 100 GB/s inter-node fabric). A model keyed on tp > GPUsPerNode alone would wrongly derate this part: the condition is the link, not the chassis count, and the step is at the rack boundary. The descriptor also states inter_rack_latency: 5 µs — a rack-boundary latency figure the catalog has no field for, so it lives in blis-registry with the other floors, as it does for gb200.

    _comment_sm SMCount is the count of ENABLED Streaming Multiprocessors per GPU, 152, from direct measurement on GB300 systems. FlashInfer's SM103 dispatch-plan tests record measured counts of B200 148, GB300 152 (JHB nodes) and key the sm_103a plan on 152 (https://github.com/flashinfer-ai/flashinfer/blob/26fe42d91acc1d56bd27560f64e9bf727d623cca/tests/experimental/test_cake_kimi_k3_fp8_projection.py#L65-L68); sm_103a is this part's architecture, matching the AISimulate descriptor's sm_version: 103. This is a PER-GPU figure, not a per-rack one — the cost model reads it per device. The measured 152 supersedes a B300 die-sharing inference of 148 that an earlier draft carried: the AISimulate descriptor cited above for FLOPs and HBM states no SM count (only sm_version: 103), NVIDIA's Blackwell Ultra architecture blog states 160 SMs across the two dies in the FULL implementation and footnotes that available SM count varies by SKU (https://developer.nvidia.com/blog/inside-nvidia-blackwell-ultra-the-chip-powering-the-ai-factory-era), and no NVIDIA datasheet publishes an enabled count — so the measured 152 (between B300's 148 and the full-die 160) is the best-attested value and is cited rather than inferred. The cost model uses SMCount for two things: the per-SM share of peak FLOPs, and the 12-SM derate a Triton-path KV fetch withholds while it overlaps a forward pass (cost model §8.3), which is 7.89% at 152 SMs.
